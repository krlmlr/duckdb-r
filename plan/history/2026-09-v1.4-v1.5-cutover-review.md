# The review that prepares the v1.4 and v1.5 cutovers

*A record, not a leaf.*
On 2026-09-04 the forward counterparts of `v1.4-andium` and
`v1.5-variegata` had both caught up with the series they replace,
and this file is what was checked before handing the swap to a human:
the gates the cutover rests on, every vendored commit that adapted the
glue on either lineage, and what the swap changes for the branch
r-universe builds from.
The cutover itself is owned by
[`.claude/skills/series-forward.md`](/.claude/skills/series-forward.md)
and [`operations/vendoring/series-loop/`](/handbook/operations/vendoring/series-loop/README.md),
and the invariant it rests on by
[`branches/invariants/`](/handbook/branches/invariants/README.md);
where one of those and this record disagree, they are right.
Every SHA below names a commit on the series refs in the fork,
so the reading can be redone without this file —
the refs move, so redo it before acting on it.

## Where the four series stood

* **`v1.4-andium`** — `-green` = `-dev` = `97017f595`,
  `-fwd-green` = `-fwd-dev` = `6bab26d2c`.
  Both vendor `duckdb/duckdb@6fc5718088`, which is upstream's tip:
  the branch has not moved since 2026-07-07.
  Nothing in flight on either side; both at version `1.4.5.9000.1`.
* **`v1.5-variegata`** — `-green` `0fc50e60a`, `-fwd-green` `ef0897ca6`,
  both vendoring `f3be2750f5` at `1.5.5.9013.33`.
  One commit in flight on each side,
  `66f42362a` and `2c0ef2757`, both vendoring `2f10cfb426` —
  again upstream's tip — and both already holding a `success` verdict,
  so the next firing moves both greens up by one.

Both seeds are read from the branch rather than assumed:
`v1.5-variegata` was seeded from `main`
(the seed sits two flavor commits above the merge base),
`v1.4-andium` from its release line
(56 commits of that line lie between the merge base and the seed),
which is what makes it the frozen series the loop treats it as.

## The gates, and what each answered

* **Coverage** — passes trivially on both:
  the forward green vendors the same upstream commit as the base green.
  Checked with `git merge-base --is-ancestor` in an upstream clone,
  as `scripts/series-cutover.sh` does;
  a commit-only clone (`git clone --bare --filter=tree:0`) is enough,
  since the gate asks about ancestry and nothing else.
* **Convergence** — `scripts/series-converge.sh` reports CONVERGED on
  both, with every difference in its explained classes:
  `README.md` alone on `v1.4-andium` (0/38);
  `README.md` (3/1), `.github/README.md` (4/2) and `NEWS.md` (137/0)
  on `v1.5-variegata`.
  The same three paths, and no others, separate `-green` from
  `-fwd-green`.
  Each was read rather than filed away; what they hold is below.
* **The replay's tree check** — `-build` and `-fwd-build` are identical
  under `src/duckdb/` and `patch/` on both series.
* **What r-universe made of the greens** — all four build on all 15
  targets: the base greens in the `duckdb` universe,
  the forward greens in the `krlmlr` universe
  (`scripts/r-universe-check.sh`, 2026-09-04).
  The packages the swap puts in front of consumers have therefore
  already been built on the platforms the per-commit gate never reaches.
* **Structure** — no merge commit above either seed on any of the four
  `-dev` branches, and neither forward green is an ancestor of its base
  green, so neither is cutover litter.

## Every vendored commit that adapted the glue

Glue is `src/` without the engine, `R/`, `NAMESPACE` and
`inst/include/`, as `scripts/series-glue.sh` defines it;
the review also read `tests/` and `patch/`,
since a vendor commit CI repaired may carry either.

**`v1.5-variegata`: none in the buffer.**
The buffer holds 34 vendor commits on each lineage,
covering the 43 first-parent upstream commits from `53395dda` to
`2f10cfb4` inclusive (nine changed nothing the vendored tree carries),
and not one of them touches a path outside `src/duckdb/`,
`DESCRIPTION` and `R/version.R`.
The three oldest — `53395dda`, `f1234115`, `02f0e5b2` — carry an
`R-side fix` section headed *Forward-port `main`'s glue*,
left by the 2026-07-29 replay that built this chain,
whose glue then had to be brought back to `main`'s.
That diff no longer exists in the commits:
the glue at each of the three equals the seed's, on both lineages.
The prose is history, not a change to look for.

**`v1.5-variegata`: what `-dev` carries came from `main`.**
Thirty commits on the base `-dev` touch glue and 23 on the forward,
and all but one are stage-4 ports — cherry-picks of `main` commits,
by trailer — never a vendor commit.
The one exception is the base's `4d2adf294`,
which renames the Windows export list to the series' flavor by hand,
because a port had planted the file under its mainline name.
Of the seven the base carries and the forward does not,
six (the handbook MVP and its two follow-ups, the Windows export list,
the CMake removal, the extension-install expectation)
are in the forward seed's ancestry,
and the seventh is that rename, which the forward's own seeding
performed on the file it found;
so the glue trees are identical at the two tips.

**`v1.5-variegata`: the patch stack moved four times.**
On the base `-dev`, `0034` (the unity-build `ERROR` undef,
from stage 3's read of a Windows r-universe build),
`0003` (the re2 fix over the pragma,
[#2492](https://github.com/duckdb/duckdb-r/pull/2492)),
`0029` (touched by the README rewrite,
[#2558](https://github.com/duckdb/duckdb-r/pull/2558))
and `0009` with `0035`–`0038` (the warning-free tree,
[#2617](https://github.com/duckdb/duckdb-r/pull/2617)).
The forward carries the last three; `0034` is in its seed.
`patch/` is identical at the two tips.

**`v1.4-andium`: one vendor commit, adapted on one side only.**
The base `-dev`'s `3f448688f` folds three CI-demanded fixes into the
single vendor commit, on 2026-07-30:
`^\.claude$` in `.Rbuildignore`, an `env_keep` line so `sudo` on
ubuntu-26.04 stops stripping the pak library variables,
and `tzdata-legacy` plus three `PST8PDT` skips in `test-DBItest.R`.
The forward's twin `294f59620` carries none of them,
because the forward's seed was regenerated on
`v1.4-andium@2b5afce5a`
([#2433](https://github.com/duckdb/duckdb-r/pull/2433)),
which holds those four files byte-for-byte as the base vendor commit
left them.
No glue, no test and no patch entry differs between the two tips.

## What the swap changes for consumers

* **`v1.5-variegata` gains the right README.**
  The base still describes itself as
  "the LTS version 1.3 of DuckDB"; the forward names its flavor.
  `NEWS.md` gains the `1.5.5.9008` to `1.5.5.9010` entries the forward
  seed carried; the base stopped at `9007`, where the port learned to
  hold `main`'s version bumps back
  ([#2526](https://github.com/duckdb/duckdb-r/pull/2526)).
* **`v1.4-andium` loses two README sections.**
  The base `-dev` holds the `Flavors` table and the `Documentation`
  section, ported whole on 2026-08-02
  ([#2438](https://github.com/duckdb/duckdb-r/pull/2438),
  [#2451](https://github.com/duckdb/duckdb-r/pull/2451),
  [#2452](https://github.com/duckdb/duckdb-r/pull/2452))
  before the port learned to recognise a frozen series
  (`feat(series-port): Detect a frozen series, and let it skip the port`,
  `f8b11785d` on `main`, 2026-08-04);
  the forward's seed comes from the release line,
  which never had them, and a frozen series ports nothing that would
  bring them back.
  `series-converge.sh` explains the difference correctly —
  each branch carries its seed's wording —
  but here the base's wording is the better one,
  and the swap makes the forward's the one r-universe shows.
  `cf1aed093` on `v1.4-andium-fwd-dev` already took the base's copy of
  the seven documents `series-converge.sh` reported as unexplained;
  `README.md` was not among them only because the script explains it.
  Taking it the same way, before the swap,
  costs one CI cycle for the forward green to catch up and leaves the
  `v1.4-andium` reading IDENTICAL.
  Accepting the loss is the other choice, and it is the operator's.
* **The stray commit on `v1.4-andium-build` goes.**
  Its tip `f52ed130b` is a `chore: Auto-update from GitHub Actions`
  bump of `Config/roxygen2/version`, pushed onto the buffer by the
  whole-branch check racing `each-rcc` on a series ref —
  the base seed predates the fix for that race, `5a36ccd1e`,
  and the forward seed includes it.
  The swap replaces the buffer with one that never had the commit;
  the pin it carried lives on `-dev` in the tooling sync
  (`556f998b0`) either way.

## What the review found beside the cutover

* **The buffer's patch stack drifts where an entry was edited.**
  At the same upstream commit, `v1.5-variegata-build` and
  `v1.5-variegata-dev` differ in `patch/0009-Remove-stderr-for-zstd.patch`
  and the four lines of `zdict.cpp` it removes:
  [#2617](https://github.com/duckdb/duckdb-r/pull/2617) edited that
  existing entry as well as adding `0035`–`0038`,
  and the stage-5 carry (`8ec275a02`) mirrored the four new entries onto
  the buffer and not the edit.
  The same drift is on the forward pair and, larger, on `main`.
  Until an edited entry is carried like a new one,
  every tree the buffer regenerates keeps the dead code the edit removes,
  and the next commit to reach `-dev` from it arrives with the warnings
  the gate rejects.
  Identical on both lineages, so the swap neither fixes nor worsens it.
* **`scripts/series-glue.sh` read the wrong span for these series.**
  Given a series name it anchored on the merge base with `main`,
  which for `v1.4-andium` lies 56 release-line commits below the seed:
  seven of that line's own commits were listed as this series' glue,
  and on both series the seed's own version commit was listed with them.
  In a shallow clone the merge base is empty and the script exited 1
  without a word.
  Fixed with this record: the span now starts at the seed's tip,
  the merge base serves only a branch that has no seed,
  and an anchor that cannot be found is named on stderr.
* **`duckdb.1.4` is red on Windows arm64**, both R versions,
  in the `duckdb` universe.
  That is the LTS flavor built from `v1.4-andium-lts`,
  not a series ref, and not this cutover's.

## Running it

From a terminal, with an upstream clone beside the checkout:

```sh
git clone --bare --filter=tree:0 https://github.com/duckdb/duckdb ../duckdb
scripts/series-cutover.sh v1.4-andium origin ../duckdb
scripts/series-cutover.sh v1.5-variegata origin ../duckdb
```

Each run fetches, prints the coverage lines and the convergence report,
lists the four moves, and asks for the series name.
As read on 2026-09-04 the moves are
`v1.4-andium`: `-build` and `-build-base` `f52ed13` → `7aa50fb`,
`-dev` and `-green` `97017f5` → `6bab26d`;
`v1.5-variegata`: `-build` `affd686` → `a67363a`,
`-build-base` `d0187f2` → `529cf4b`,
`-dev` `66f4236` → `2c0ef27`, `-green` `0fc50e6` → `ef0897c`.
The `v1.5-variegata` refs will have moved by the time anyone types the
name — the loop fires between readings — and the per-ref lease makes a
push against a moved ref fail rather than swap over it;
rerunning the script re-reads and re-prints.
Order does not matter; `v1.4-andium` first is the smaller move.

Afterwards: the script deletes the four `-fwd-*` refs,
and says so if the remote refuses, in which case they go via the forge
UI — until they are gone the loop reads them as cutover litter.
The `krlmlr` universe's `duckdb.1.4.dev` and `duckdb.1.5.dev` entries
point at `-fwd-green` refs that then no longer exist;
the `duckdb` universe rebuilds from the swapped greens on its own.
